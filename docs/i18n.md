# Languages

Every sentence a person reads while signing in comes from a message catalogue.
Adding a language is adding one file; nothing is compiled, registered or
rebuilt.

## The thirty-second version

```sh
signari i18n keys > keys.txt                 # every message key
$EDITOR ./theme/locales/fr.json              # write them
signari i18n status -theme-dir ./theme       # exits non-zero if incomplete
SIGNARI_THEME_DIR=./theme signari serve
```

The catalogue lives in the **same directory as page overrides**, under
`locales/`, because they are one thing to an operator: what this deployment's
sign-in pages say.

## What ships

| | |
|---|---|
| `en` | The reference. Complete by definition — everything falls back to it. |
| `ar` | Complete, and right-to-left. |

Two, not twenty-five. The machinery is the part that was missing, and it is
done: a language is a JSON file, checked by `signari i18n status`, advertised in
discovery, and rendered with correct plurals and text direction without anything
else changing.

**We have not shipped machine-translated languages, and that is deliberate.**
These pages say things like *"Nobody legitimate will ask you to enter a code
they sent you"* and *"Only continue if you started this yourself"*. A
mistranslation there does not read as a typo — it reads as advice, and it is the
advice standing between somebody and a phone call from a stranger. A language
belongs here when a person who speaks it has read those sentences.

## Rewording without forking a page

The catalogue is not only for translation. Changing what a page says used to
mean copying the whole page into a theme directory, where it stopped receiving
upstream fixes — including security fixes to the form it contains.

```json
{ "login.heading": "Sign in to Example Corporation" }
```

That is a complete `locales/en.json`. Everything else keeps coming from the
built-in catalogue, and `login.html` is still ours, so it still gets fixes.

**Wording goes in a catalogue. Structure goes in a page override.** If you find
yourself overriding a page to change a sentence, use the catalogue instead.

## How the language is chosen

1. **`ui_locales`** — the OIDC request parameter. The relying party asked
   explicitly, usually because the person already chose a language in the
   application that sent them. Being sent to a sign-in page in a different
   language than the app you came from is the failure this parameter exists to
   prevent.
2. **`Accept-Language`** — what the browser was configured with.
3. English.

`ui_locales` survives the whole flow. The sign-in pages round-trip the original
authorization query through a hidden `authz` field, so the parameter is still
there on the POST that follows and on the consent screen after that — without it,
the first page would honour the request and every page after would quietly fall
back to the browser.

Region subtags resolve to the base language: a request for `pt-BR` is answered in
`pt` if that is what is loaded, rather than falling through to English because
the file happens to be named `pt.json`.

Discovery advertises `ui_locales_supported`, built from what actually loaded
rather than a list maintained beside it. It is omitted when only one language is
present, because a list containing just `en` tells a relying party nothing.

## Writing a catalogue

A message is a string, or an object of plural forms:

```json
{
  "login.heading": "Connexion",
  "fclogout.progress": {
    "one":   "Déconnexion de {n} application. Cette page continuera seule.",
    "other": "Déconnexion de {n} applications. Cette page continuera seule."
  }
}
```

**Plurals are not two forms.** English has two; Arabic has six; Russian puts 21
in the same form as 1 and 5 in another; French counts 0 as singular. Which form
is used is decided by CLDR, so a translator writes the forms their language
actually has and no call site needs to know how many that is. The categories are
`zero`, `one`, `two`, `few`, `many` and `other`. Every language has `other`, and
a message without it is refused.

`{Placeholder}` names come from the page's own data — `{Number}`, `{Address}`,
`{ClientName}`. `{n}` is the count in a plural message. A placeholder with no
value is left visible rather than blanked, for the same reason a missing key
renders as the key: a hole in a page that still looks finished is worse than an
obvious mistake.

Messages may contain HTML, because a sentence that emphasises the address a code
went to should not have to be three fragments in English clause order. Values
substituted into them are escaped, and a URL substituted into an `href` is
checked for a scheme that can execute.

## Text direction

Decided by the language's **script**, not by a list of languages: Kurdish is
right-to-left in Arabic script and left-to-right in Latin, and a per-language
list gets that wrong in whichever direction it was written. `<html>` carries
`lang` and `dir`, and the stylesheet needs no changes — the layout mirrors
itself.

Values substituted into a sentence are wrapped in Unicode isolates, so a phone
number or an email address keeps its own reading order. Without that, the masked
number `+44 7700 •••912` displays as `+44 7700 912•••` inside an Arabic
sentence — on the page whose entire purpose is letting somebody check which
number their code went to.

## What is NOT translated, and why

**Scope descriptions a client registered.** The consent screen describes the
scopes it knows — `profile`, `email`, `offline_access`, `address`, `phone` — and
shows anything else exactly as the client registered it. Those words are the
client's, and guessing at them on a screen where the text *is* the decision
would be worse than leaving them alone. RFC 7591 §2.2 defines how a client can
register localised metadata; honouring that is not implemented, and this is the
honest behaviour until it is.

**Authorization details.** The rows on a consent screen for a payment or a
specific operation come from the relying party, verbatim.

**Operator-authored prompts.** Terms-of-use text and custom fields are written by
whoever configured them.

## Checking

```sh
signari i18n list      # what this deployment can render
signari i18n status    # what is missing, non-zero if anything is
signari i18n keys      # every key, to write a catalogue against
```

`signari doctor` reports a loaded language that is incomplete, because that is
the failure that looks fine from the server: the page renders, the fallback
fills the gaps in English, and the only person who sees the result is somebody
being asked for their password on a page written half in one language and half
in another.

## The console

The Filament admin console is separate and uses Laravel's own conventions:
`admin/lang/<tag>.json`, keyed by the English source, with `__()` at the call
site. Filament ships catalogues for its own chrome in sixty-three languages;
`lang/` carries the domain terms that are ours. Both halves have to be present
or the console renders half in each language.

The console negotiates from `Accept-Language` alone. There is no `ui_locales`
equivalent because nothing sends a console request on somebody's behalf, and
there is deliberately no language switcher writing to a cookie: a preference an
operator sets belongs on their account, and until there is a column for it,
honouring the browser is the honest behaviour rather than inventing a third
place for state to live.

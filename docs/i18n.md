# Languages

## Introduction

People read Signari's sign-in pages in their own language, when Signari has it.
Every sentence a person reads while signing in comes from a "message
catalogue": a file that holds each of those sentences in one language.

Signari ships English and Arabic. Adding a language is adding one file. Nothing
is compiled, registered or rebuilt.

Catalogues live in your theme directory, `SIGNARI_THEME_DIR`, under `locales/`.
`signari i18n status` checks that each one is complete.

## The thirty-second version

To add a language, list every message key, write a catalogue, check that it is
complete, and serve it:

```sh
signari i18n keys > keys.txt                 # every message key
$EDITOR ./theme/locales/fr.json              # write them
signari i18n status -theme-dir ./theme       # exits non-zero if incomplete
SIGNARI_THEME_DIR=./theme signari serve
```

The catalogue lives in the **same directory as page overrides**, your own
copies of Signari's pages (see [theming](theming.md)). It sits under
`locales/`, because to an administrator they are one thing: what this
deployment's sign-in pages say.

## What ships

Signari ships two languages:

| | |
|---|---|
| `en` | The reference. Complete by definition — everything falls back to it. |
| `ar` | Complete, and right-to-left. |

Two, not twenty-five. The machinery was the part that was missing, and it is
done. A language is a JSON file. `signari i18n status` checks it, discovery
advertises it, and it renders with correct plurals and text direction, without
anything else changing.

**Signari has not shipped machine-translated languages, and that is
deliberate**. These pages say things like *"Nobody legitimate will ask you to
enter a code they sent you"* and *"Only continue if you started this
yourself"*. A mistranslation there does not read as a typo. It reads as advice,
and it is the advice standing between somebody and a phone call from a
stranger. A language belongs here when a person who speaks it has read those
sentences.

## Rewording without forking a page

The catalogue is not only for translation. Changing what a page says used to
mean copying the whole page into a theme directory. There, the copy stopped
receiving upstream fixes, including security fixes to the form it contains.

Now a catalogue can change one sentence and nothing else. This is a complete
`locales/en.json`:

```json
{ "login.heading": "Sign in to Example Corporation" }
```

Everything else keeps coming from the built-in catalogue. `login.html` is still
Signari's, so it still gets fixes.

**Wording goes in a catalogue. Structure goes in a page override.** If you find
yourself overriding a page to change a sentence, use the catalogue instead.

## How the language is chosen

Signari looks for a language in this order:

1. **`ui_locales`**, the OpenID Connect (OIDC) request parameter. The
   application asked explicitly, usually because the person already chose a
   language in the application that sent them. Being sent to a sign-in page in
   a different language from the application you came from is the failure this
   parameter exists to prevent.
2. **The person's own choice**, the **Language** selector on `/account`. It is
   saved on the account (`users.locale`, the language their notices are
   written in). It is also saved in a cookie, `__Host-signari_lang`, which every
   page reads, the sign-in page included. Signing in on another browser sets
   the cookie there too. A browser's setting says nothing about who is reading
   on a shared or borrowed machine, so this choice comes before it. Choosing
   "this browser's setting" clears both.
3. **`Accept-Language`**, what the browser was configured with.
4. English.

The selector names each loaded language in that language, from its catalogue's
`language.name`. An administrator's catalogue that leaves the key out is listed
by its tag. Until October 2026, nobody could choose: `signari user locale` set
the notices' language, and pages followed the browser alone.

`ui_locales` survives the whole flow. The sign-in pages round-trip the original
authorization query through a hidden `authz` field. So the parameter is still
there on the POST that follows, and on the consent screen after that. Without
it, the first page would honour the request, and every page after would quietly
fall back to the browser.

Region subtags resolve to the base language. A request for `pt-BR` is answered
in `pt` if that is what is loaded. It does not fall through to English because
the file happens to be named `pt.json`.

Discovery advertises `ui_locales_supported`, built from what actually loaded,
not from a list kept beside it. It is left out when only one language is
present, because a list containing only `en` tells an application nothing.

## Writing a catalogue

A message is a string, or an object of plural forms:

```json
{
  "login.heading": "Connexion",
  "fclogout.progress": {
    "one":   "Déconnexion de {n} application. Cette page continuera seule.",
    "other": "Déconnexion de {n} applications. Cette page continuera seule."
  }
}
```

**Plurals are not two forms.** English has two, and Arabic has six. Russian
puts 21 in the same form as 1, and 5 in another. French counts 0 as singular.

The Unicode Common Locale Data Repository (CLDR) decides which form is used. So
a translator writes the forms their language actually has, and no call site
needs to know how many that is. The categories are `zero`, `one`, `two`, `few`,
`many` and `other`. Every language has `other`, and a message without it is
refused.

`{Placeholder}` names come from the page's own data, such as `{Number}`,
`{Address}` and `{ClientName}`. `{n}` is the count in a plural message.

A placeholder with no value is left visible, not blanked, for the same reason a
missing key renders as the key. A hole in a page that still looks finished is
worse than an obvious mistake.

Messages can contain HTML. A sentence that emphasises the address a code went
to should not have to be three fragments in English clause order. Values
substituted into messages are escaped. A URL substituted into an `href` is
checked for a scheme that can execute.

## Text direction

Text direction is decided by the language's **script**, not by a list of
languages. Kurdish is right-to-left in Arabic script, and left-to-right in
Latin script. A per-language list gets that wrong in whichever direction it was
written. `<html>` carries `lang` and `dir`, and the stylesheet needs no
changes: the layout mirrors itself.

Values substituted into a sentence are wrapped in Unicode isolates: marks that
give a stretch of text its own reading order. So a phone number or an email
address keeps its own direction. Without that, the masked number
`+44 7700 •••912` displays as `+44 7700 912•••` inside an Arabic sentence. That
would happen on the page whose entire purpose is letting somebody check which
number their code went to.

## What is not translated, and why

**Scope descriptions an application registered.** The consent screen describes
the scopes it knows: `profile`, `email`, `offline_access`, `address` and
`phone`. It shows anything else exactly as the application registered it. Those
words are the application's. Guessing at them on a screen where the text *is*
the decision would be worse than leaving them alone.

**An application's name** is the application's own words too. It is shown in
the reader's language only when the application gave a name in it, as RFC 7591
§2.2's `client_name#<tag>`. The name can come from its registration,
`signari client name`, the Admin API or a configuration file. Otherwise it is
shown as registered. See
[the name in other languages](dynamic-registration.md#the-name-in-other-languages).

**Authorization details.** The rows on a consent screen for a payment or a
specific operation come from the application, word for word.

**Prompts an administrator wrote.** Terms-of-use text and custom fields are
written by whoever configured them. What is wrong with an answer is the
catalogue's, though, with the fields named as the administrator labelled them.

**A protocol error meant for an application**. An `error_description` in an
OAuth or [Security Assertion Markup Language (SAML)](saml.md) answer is for the
developer of the application that sent the request. So is the reason an
authorization request was refused. Both stay in the specification's terms.

Everything a person is told about their own input or their own sign-in is said
through the catalogue:

- a refused password, and what a weak one is built around;
- a refused attribute value;
- a phone number;
- an address change;
- an enrolment step;
- a sign-up;
- a sign-in at an upstream provider.

Until November 2026, each of those was an English sentence for every reader,
and in places an error's own text. The helpers that render them take a message
key. `TestEveryMessageKeyIsUsedAndEveryUsedKeyExists` reads the keys from the
code, and fails on any missing from `en.json`. So an English sentence handed to
one of them fails the build.

## Checking

Three commands show what a deployment can render, and what is missing:

```sh
signari i18n list      # what this deployment can render
signari i18n status    # what is missing, non-zero if anything is
signari i18n keys      # every key, to write a catalogue against
```

`signari doctor` reports a loaded language that is incomplete. That failure
looks fine from the engine's side: the page renders, and the fallback fills the
gaps in English. Only one person sees the result: somebody being asked for their
password, on a page written half in one language and half in another.

### Three checks, not one

`i18n status` refuses a catalogue for three separate reasons. Each is a failure
that a count of keys cannot see:

| | |
|---|---|
| `PARTIAL` | Keys are **missing**. Each one renders the English string mid-page |
| `STALE` | Keys exist that English does not have. Almost always a key **renamed** in English while the translation kept the old name — so the file looks finished while the *new* key falls back |
| `SUBST` | A message does not carry the same **substitutions**. Dropping one leaves a sentence with a hole where a value belongs; adding one renders `{Expires}` literally, because nothing substitutes a name the caller never passes |

Substitutions are checked **per plural form**, which matters more than it
sounds. A translation can carry `{n}` in its singular, and drop it from its
plural. The union of placeholders still matches, so a naive check passes. Only a
reader with three of something sees the hole. Each form is measured separately.

The exception is deliberate and linguistic. The CLDR categories `zero`, `one`
and `two` are selected by an exact value. So the number is already known, and a
language can leave it unwritten. English's own `connected.sessions` says "No
active session." for zero. Arabic's dual *تطبيقين* already means "two
applications", so writing `{n}` there would render "2 two-applications". `few`,
`many` and `other` cover a range, so the count is variable and is still
required.

### Why the shipped languages are few

Each shipped language is **whole**, and that is enforced, not only intended. The
build fails on any of the three conditions above.

The alternative is worth naming, since a language count is the number people
compare. A widely deployed identity provider in this field ships around forty
sign-in languages. They were measured against its own English bundle of 525
keys on 25 August 2026, and run from 99% complete down to 83%.

Those are real translations by real contributors. Yet the thinnest of them
still means a reader meets English on roughly one key in six. The reader meets
it silently, because a fallback is indistinguishable from a sentence that was
always meant to read that way.

Adding a language here is one file, and needs no rebuild (see
[Writing a catalogue](#writing-a-catalogue) above). `signari i18n status` tells
you exactly what is left before you ship it. It exits non-zero, so a deployment
pipeline can refuse a partial one.

## The console

The console is separate. It is built with Filament, and uses Laravel's own
conventions: `admin/lang/<tag>.json`, keyed by the English source, with `__()`
at the call site. Filament ships catalogues for its own chrome in sixty-three
languages. `lang/` carries the domain terms that are Signari's own. Both halves
have to be present, or the console renders half in each language.

The console negotiates from `Accept-Language` alone. There is no `ui_locales`
equivalent, because nothing sends a console request on somebody's behalf.

There is deliberately no language switcher writing to a cookie. A preference an
administrator sets belongs on their account. Until there is a column for it,
honouring the browser is the honest behaviour, instead of inventing a third
place for state to live.
